Product Overview

C-ECM Documentation

C-ECM is a unified content-services layer: one login, one set of folders/files/search/workflow/security concepts, sitting in front of whatever document repositories your organization already runs — IBM FileNet, S3-compatible object storage, Google Drive, Box, SharePoint, and dozens of other connectors (54 registered today, at varying levels of verification — see Integrations & Connections) — instead of asking every user to learn each backend's own client.

What is the platform?

Most organizations end up with content scattered across several repositories: a legacy ECM like FileNet for regulated records, a cloud drive for day-to-day collaboration, an object store for bulk archives, and a handful of point solutions bolted on over the years. Each has its own login, its own permission model, its own search box.

C-ECM doesn't replace any of those systems or migrate their content. It connects to them (a "Connection" per backend, per account) and exposes one consistent REST API and web UI on top: the same folder/file operations, the same tagging/commenting/metadata model, the same approval-workflow engine, the same access-control model, and the same search box, regardless of which backend a given connection actually talks to.

Key capabilities

Unified content access

Browse, upload, download, version, tag, comment, and organize files and folders across 54 registered storage backends through one interface.

Access control

Group-based feature permissions plus opt-in, per-file/per-folder view/edit grants layered on top of each backend's own native permissions.

Approval workflows

Multi-step, multi-document approval requests with user- or group-based assignment, quorum, and mid-flight reassignment.

E-signature

Send documents for signature via DocuSign and track envelope status without leaving the app.

Retention & legal hold

Policy-driven retention with a scheduled background sweep that reviews, archives, or deletes due records.

AI document intelligence

Summarize, classify, extract from, and chat with document content using a configured AI backend.

AI Agents

Publish a scoped, chat-based AI assistant over a specific folder or file, with a public link, embeddable widget, and lead capture.

Single sign-on

SAML SSO into C-ECM itself, independent of whatever credentials each connected backend needs.

Governed integrations

Webhooks, an audited activity log, and a documented REST API for building on top of the platform.

Key benefits

  • No content migration. Connect to existing repositories as they are; nothing has to move.
  • One access-control story. Group membership and per-resource grants work the same way no matter which backend a folder actually lives on.
  • One audit trail. Every action — across every connected backend — lands in the same activity log.
  • Extensible by design. A single storage-provider interface means a new backend is an implementation of one interface, not a new application.

Who should use it?

  • End users who need to find, share, and act on documents that live in more than one system.
  • Approvers and managers who review and sign off on documents via workflows and e-signature.
  • Administrators who manage users, groups, connections, retention, and platform-wide settings.
  • Developers and integrators building on the REST API or adding a new storage connector.
  • AI/agent builders configuring document-intelligence features or publishing a scoped AI agent.

Supported use cases

C-ECM's capabilities are generic (folders, files, metadata, workflow, security) rather than vertical-specific — there's no built-in "Healthcare edition" or "Legal edition." Chapter Business Use Cases walks through how the same generic building blocks apply to HR, legal, finance, healthcare, banking, insurance, government, and manufacturing scenarios.

Product terminology

A handful of terms recur throughout this documentation — see the full Glossary for the complete list. The essentials: a Connection is one authenticated link to one storage backend; a Resource is a file or folder inside a connection; a Group grants its members a set of Features (app-wide capabilities like "manage users"); an Access Grant is a separate, opt-in view/edit permission on one specific resource.

Get Started / Getting Started

Getting Started

Quick Start

A first pass through the platform in the order most new users hit it: log in, connect a backend, create your first document, search for it, request approval on it, and (if configured) ask AI about it.

First login

Open the C-ECM web app in a browser. On first run the server seeds one built-in account (username admin, password admin by default — both overridable via FD_APP_USERNAME / FD_APP_PASSWORD, see Configuration Reference). Sign in with those credentials, or via SAML SSO if your administrator has configured it (a "Sign in with SSO" option appears automatically once SAML is enabled).

Before going further

Change the default admin password (or disable the default account) before exposing the server beyond your own machine — it's a well-known default, not a secret.

First connection

Everything else in C-ECM happens inside a connection — one authenticated link to one storage backend. Go to Settings → Connections, pick a provider, and either supply credentials directly (for backends like FileNet, S3-compatible storage, or a local disk folder) or complete an OAuth consent flow (for Google Drive, Box, Microsoft 365, and the other OAuth-based connectors). See Integrations & Connections for the full provider list and what each one needs configured first.

First folder

With a connection selected, the Drive view shows that backend's root folder. Use New → Folder to create one — it's created directly in the connected backend, not in some separate C-ECM database.

First document

Drag a file onto the Drive view, or use New → Upload. Re-uploading to the same path creates a new version rather than overwriting — see Content & Document Management for the full versioning model.

First search

The search box in the top bar searches the active connection by default. Switch to Global Search (left navigation) to search every connection you have access to at once — see Search for how results and permissions interact.

First workflow

Right-click a file or folder and choose Request Approval (this option only appears once at least one workflow definition exists — an administrator creates these under the Approvals hub's Designer tab first). Pick a workflow, and it moves into the current step's assigned reviewer's Inbox. See Workflows & Approvals for the complete model, including multi-document requests, group-based assignment, and reassignment.

First AI interaction

AI document intelligence only becomes available once an administrator configures an AI backend under Settings → Admin → AI (see AI Capabilities for what's supported and required). Once configured, AI actions appear against individual documents in the viewer.

First AI Agent

From a file or folder's context menu, choose Create AI Agent to scope a chat assistant to that resource (this also requires an AI backend to be configured first). See AI Agents for the full creation flow and what a published agent's public page looks like to an end visitor.

First integration

"Connecting" a storage backend (above) is the most common integration. For system-to-system integration against the REST API directly, see API Reference — authenticate with POST /auth/login and browse the live, interactive schema at your server's /docs endpoint.

Core Concepts / Workflows & Approvals

Workflows

Implemented

Workflows & Approvals

A lightweight, multi-step approval engine: define a reusable sequence of review steps once, then request approval against one or more documents at a time, with quorum voting, group-based assignment, and mid-flight reassignment.

What is a workflow?

A workflow definition is a named, reusable template: an ordered list of steps, each with a set of assignees (specific users and/or groups — an empty list means "any authenticated user") and a required approvals count (a quorum). A workflow instance is created when someone requests approval against one or more real documents using a definition; it tracks its own status, current step, and vote history independently of the definition it was started from.

Architecture

Figure — the complete state machine. act_on_step() only allows these transitions.

Definitions and instances are stored in their own SQLite file (workflows.db), managed entirely by workflows_store.py; routers/workflows.py owns the HTTP boundary. Two design points matter for correctness:

  • Multi-document requests. An instance can cover a set of documents (workflow_instance_resources), not just one — documents can be added to or removed from an in-review request, down to a minimum of one.
  • Per-instance step snapshot. Each instance snapshots its definition's steps at creation time (steps_json). Reassigning a step only ever rewrites that one instance's own copy — never the shared, reusable definition, so reassigning one request never silently changes another request built from the same template.

Designing a workflow

Only accounts with the manage_workflow_definitions feature (or a superadmin) can create or delete definitions, from the Approvals hub's Designer tab. Each step needs a name, a required-approvals count, and its assignees — chosen from real user and group checklists (not free-text), specifically to prevent an unrecognized username from silently creating a step nobody can ever act on.

Starting a request

Right-click one file or folder and choose Request Approval for a single-document request, or select several items and use the same action in the bulk toolbar to bundle them into one request. Starting a request requires edit access (see Security) on every document being attached — not just the first one.

Tasks, assignment, and quorum

A step's assignees can be individual users, groups (any current member is eligible), or left empty (open to anyone authenticated). Eligibility is resolved live — adding someone to a group makes them eligible to act on any step assigned to that group without touching the workflow itself. Required approvals counts individual approve votes on the current step, not the number of assignee entries — a step assigned to a 10-person group with "required approvals: 2" still only needs two of that group's members to approve.

Approvals and rejections

A single authorized rejection ends the whole instance immediately (status rejected) — there's no quorum on rejection, matching how approval workflows conventionally work: unanimity to pass, not to fail. Reaching the required approval count on the current step advances to the next step, or completes the instance (status approved) if it was the last step. Each person can vote once per step.

Reassignment

An in-review step can be reassigned to a different user or group by: a superadmin, anyone with manage_workflow_definitions, the original requester, or whoever the step is currently assigned to (a self/delegate handoff — useful when a reviewer is unexpectedly unavailable). Reassignment only ever touches the current step of that one instance.

Adding or removing documents

The same set of people above can add another document to an in-review request, or remove one — down to a floor of one remaining document (a request can never be left with zero). Adding a document still requires edit access on it.

Cancellation

Only the original requester or a superadmin can cancel an in-review request — this is deliberately not a delegable feature, the same "override anyone's action" bypass concept superadmin has everywhere else in the app.

History and notifications

Every vote, reassignment, document addition/removal, and status change is recorded — visible inline as each instance's step timeline, and separately in the app-wide activity log. Every workflow transition also fans out as an in-app notification to all active users.

E-signature

External dependency

Send a file out for signature via DocuSign, directly from a document's context menu — a separate action from an internal approval workflow, for when a document needs a legally binding signature from someone (internal or external) rather than an in-app approval vote.

Requires a real DocuSign account

This is a genuine integration against DocuSign's documented eSignature REST API v2.1 (JWT Grant / server-to-server auth, RS256-signed) — not a simulation. It does nothing until an administrator supplies a real DocuSign integration key, impersonated user id, account id, and RSA private key. The codebase's own documentation is candid that this integration is written to DocuSign's published contract but has not been exercised end-to-end against a live DocuSign account.

  • Only files can be sent (not folders); up to 20 signers per envelope, placed on fixed signature-tab coordinates rather than content-aware anchors.
  • Sending requires both the send_esignature feature and edit-level access to the file.
  • Status (sent/delivered/completed/declined/voided) can be checked on demand, or arrives automatically via a DocuSign Connect webhook — which, on reaching "completed," downloads the signed PDF and attaches it as a new version of the original file, closing the loop with no manual step.
  • Only the original requester or a superadmin can void a pending request.
Webhook verification is opt-in

The inbound webhook is authenticated by an HMAC signature — but only if a webhook HMAC key has been configured. Without one, the endpoint accepts any POST claiming to be DocuSign (logging a warning), since there's no C-ECM session to check against a server-to-server callback. Configure FD_DOCUSIGN_WEBHOOK_HMAC_KEY before relying on this in anything beyond a demo.

Trust & Access / Security

Security

Security

Three independent, composable layers: authentication (who are you), group-based feature authorization (what can you do, app-wide), and per-resource access grants (what can you touch, on this specific file or folder).

Authentication

C-ECM has its own login, separate from the credentials each connected backend uses. Two paths mint the same kind of session:

  • Implemented Username/password. POST /auth/login checks a bcrypt-hashed password (users_store.py) and issues a JWT (HS256, PyJWT) valid for FD_JWT_EXPIRE_MINUTES (24 hours by default).
  • Config required SAML SSO. C-ECM acts as a Service Provider (saml_service.py, via python3-saml). An administrator supplies the IdP's entity id, SSO URL, and signing certificate under Settings → SSO; C-ECM auto-generates its own SP signing keypair on first use. A user who doesn't already exist is created just-in-time on first successful SSO login (matched by email), optionally into a configured default group.

Every session is tracked in-memory server-side; restarting the server invalidates every existing JWT (acceptable for a single-process, on-prem-style deployment — there is no distributed session store).

Authorization: groups & features

Figure — a user's access is the union of their groups' feature grants, plus an independent, opt-in per-resource layer underneath it.

There are no fixed roles. Instead: a fixed catalog of app-wide features (e.g. manage_users, manage_workflow_definitions, manage_resource_permissions) is defined in features.py; an administrator creates Groups, grants each group a subset of features, and assigns users to groups. A user's effective permissions are the union of every group they belong to. A superadmin flag on a user account bypasses every feature check outright.

Every protected route declares its required feature via a single shared dependency (auth.require_feature("...")) — there's no scattered, ad-hoc permission logic per route.

Per-resource access grants

Group features answer "can this user manage workflow definitions at all" — they say nothing about which specific files a user can reach. A separate, opt-in layer answers that: granting a user or group view (read-only) or edit (read/write) access to one specific file or folder.

  • A connection with no grants at all behaves exactly as before — every authenticated user has full access (today's default, unchanged).
  • The moment a folder or file receives its first grant, it becomes access-controlled: only users/groups with an applicable grant — on that resource or the nearest restricting ancestor folder — can reach it, at the level granted.
  • A grant closer to the resource overrides one inherited from a parent folder (e.g. a file-level "view" grant overrides an inherited folder-level "edit").
  • Managing grants requires the dedicated manage_resource_permissions feature — deliberately not the same as having edit access on the resource itself, so an ordinary editor can't unilaterally lock teammates out.

Encryption

Config required In transit: C-ECM itself serves plain HTTP; TLS is expected to be terminated by a reverse proxy/load balancer in front of it in any real deployment — see Installation & Deployment. Implemented At rest: every stored connection's credentials, and every secret-shaped admin setting (OAuth client secrets, the DocuSign private key and webhook HMAC key, the SAML SP's own signing private key, IBM Watson/watsonx API keys), are encrypted with a server-managed key (Fernet/AES via the cryptography package) before they ever reach disk — crypto_util.py is the single place this happens, so nothing has to remember to call it correctly per field. Non-secret settings (a client id, a tenant name, a model id) are left as plain text on purpose. Losing the server's key file makes existing encrypted rows unrecoverable, the same operational tradeoff already accepted for the session-signing key — see Configuration Reference's FD_SECRETS_KEY.

Explicitly not implemented

To be direct about what this platform does not currently provide, since real evaluation depends on knowing the gaps as much as the capabilities:

  • Not implemented LDAP / Active Directory integration
  • Not implemented Generic OIDC login (SAML is the only SSO protocol supported)
  • Not implemented Multi-factor authentication
  • Not implemented Tenant isolation / multi-tenancy — this is a single-tenant application
  • Not implemented Full-database encryption at rest (SQLCipher or equivalent) — the databases themselves are plain SQLite files; only the specific secret-shaped columns described above are individually encrypted, not every byte on disk

Connection credentials & OAuth

Each storage-provider connection holds its own credentials or OAuth tokens, independent of the C-ECM login above — see Integrations & Connections for the per-provider auth model (native credentials vs. OAuth authorization-code flow) and Configuration Reference for where each provider's client id/secret is configured.

Audit logging

Every significant action — content changes, workflow transitions, login/logout, admin changes — is recorded to an append-only activity log queryable by administrators; see Reporting, Audit & Notifications.

Security best practices

  • Change the default admin password (FD_APP_PASSWORD) before any shared or external exposure.
  • Put a TLS-terminating reverse proxy in front of the server for anything beyond local development.
  • Scope group feature grants narrowly — least privilege applies the same way here as with fixed roles elsewhere; a superadmin account should be reserved for genuine administrators.
  • Use per-resource access grants for anything genuinely sensitive rather than relying solely on group-level features, which are app-wide, not resource-specific.
  • Treat the SQLite data directory as sensitive at the filesystem level regardless — stored credentials and secrets are encrypted, but resource content, metadata, and the encryption key file itself (.secrets_key) are not.
  • Back up .secrets_key (or set FD_SECRETS_KEY from your own secrets manager) with the same care as the data it protects — losing it makes every stored connection and admin secret permanently unrecoverable, not just unreadable.

Installation

Installation & Deployment

The backend and frontend are two independent processes — a FastAPI app served by Uvicorn, and a Vite-built React SPA. By default there's no separate database server to install (SQLite, one file per store); a real deployment typically points the backend at PostgreSQL instead — see Configuration Reference → App database. This page covers a development install first; see Production deployment further down for standalone, AWS, Azure, and Windows-native paths.

Prerequisites

  • Python 3.12 recommended (3.10+ supported)
  • Node.js (a recent LTS release)
  • The application source (this repository)
  • For production deployment: Docker + Docker Compose (standalone/AWS/Azure paths), or a WebSphere Application Server + FileNet CEClient install if real FileNet content-write support is needed (Windows-native path)

Before this is really "production"

The paths above get a working, reachable deployment fast — they deliberately don't do everything a hardened production setup needs:

  • Not included TLS. Nothing here terminates HTTPS. Put a real domain + certificate in front — a cloud load balancer (an AWS ALB or Azure Application Gateway/Front Door, both handle cert provisioning/renewal), or a Certbot/Let's Encrypt sidecar added to the nginx service.   • Not included Database backups. The Postgres data volume has no automated backup schedule out of the box — either add pg_dump on a cron, or point FD_DB_HOST at a managed instance instead (AWS RDS / Azure Database for PostgreSQL) for automatic backups and HA, which FD_DB_ENGINE=postgres already supports with no code change.
  • Not included Secrets management. deploy/.env holds plaintext credentials on whatever host runs it — fine for a quick deployment, move to your cloud's secrets manager (AWS Secrets Manager / Azure Key Vault) before this holds real customer data.
  • Not implemented Scaling beyond one box. This is a single-instance deployment by design. Running more than one backend replica needs a shared session store first — sessions are held in an in-process, per-worker dictionary today (see Security → Session & token handling).

Upgrade procedure

Every store module runs its own additive-only migration on startup (new columns/tables are added; nothing is ever dropped), against whichever database engine is configured (see Configuration Reference → App database) — pulling a new version of the code and restarting both processes (or docker compose up -d --build for the standalone/cloud paths) is the upgrade procedure. There is no separate migration command to run.

Backup and restore

Manual process There is no built-in backup scheduler on any database engine. On SQLite (the development default), back up by copying the entire data directory (every *.db file plus .jwt_secret/.secrets_key) while the server is stopped, or via SQLite's own online-backup tooling if it must stay running. On Postgres/Oracle (the standalone/cloud deployments' default), use that engine's own dump/restore tooling (pg_dump/pg_restore, Data Pump) against the connection settings in Configuration Reference — or point at a managed instance (RDS / Azure Database for PostgreSQL) for automated backups instead. Either way, restore is: stop the server, restore the data, start it again. See Operations & Troubleshooting for more.

Uninstallation

Stop both processes and delete the backend's data directory, the Python virtual environment, and frontend/node_modules. Nothing is installed system-wide.

AI Capabilities

AI Capabilities

Four document-intelligence actions — summarize, ask a question, classify, suggest a workflow — plus the text-extraction step that feeds all of them. Every one of them is disabled until an administrator configures a real AI backend; nothing here works out of the box.

Backend required

Set FD_AI_BACKEND (or Settings → Admin) to one of openai, ollama, watsonx, watson_nlu, or watson_disco. The default, none, keeps every AI action returning a clean "AI is not configured" response rather than an error. See Configuration Reference for exact variable names.

Document summarization

Partial

POST /files/{file_id}/ai/summarize extracts a document's text and asks the configured backend for a 2–3 sentence summary. Behavior genuinely differs by backend, worth knowing before choosing one:

  • openai / ollama / watsonx — a real generative summary.
  • watson_nlu — not generative at all: returns Watson NLU's own "summary" feature output if present, otherwise falls back to a plain "Key topics: …" keyword list.
  • watson_disco — Discovery is a retrieval product, not a summarizer; this path only produces a real summary if watsonx is also configured as a fallback, otherwise it returns nothing usable.

Document Q&A ("Ask about this document")

Partial

POST /files/{file_id}/ai/ask answers a free-text question grounded only in that one document's extracted text — single-document, single-turn, stateless (no conversation history is kept). For watson_disco, it retrieves matching passages from the configured Discovery project and either feeds them to watsonx for a generated answer (if configured) or returns the raw retrieved passage text verbatim. For watson_nlu, this action is explicitly unsupported and returns a fixed message directing you to switch backends.

Every prompt — summarize, ask, classify — wraps the document's extracted text in an explicit "this is data, not instructions" framing before it reaches the model, specifically to defend against a document's own content trying to hijack the prompt.

Document classification & metadata auto-suggestion

Partial

POST /files/{file_id}/ai/classify suggests which existing document class a file belongs to and drafts values for that class's fields from the document's content. It's implemented and tested, but uses a first-match heuristic (stops at the first class whose fields get any suggested values, rather than scoring every class) — and, as of this audit, the shipped frontend has no button that calls it. It's a real, working endpoint without a UI home yet.

AI-powered workflow routing suggestion

Implemented

POST /files/{file_id}/ai/suggest_workflow suggests which existing workflow definition best fits a document, so a reviewer can start it with one click. Two distinct strategies, both purely advisory (a user always confirms or overrides):

  • High confidence — Watson NLU classifies the document against your actual workflow names (only when Watson NLU is configured).
  • Medium confidence — a fixed keyword table (invoice/receipt/PO → Finance Approval; contract/NDA → Legal Review; policy/compliance → Compliance Review; report/audit → Management Review; HR/onboarding → HR Approval) matched against the first 2,000 characters.

Unlike the other three actions, this one works even with no AI backend configured at all — the keyword table needs no external service.

AI Agents

AI Agents

An AI Agent is a named, chat-based Q&A assistant scoped to exactly one folder or file, publishable as a public chat link, an embeddable widget, and — uniquely — a small auto-generated marketing/demo website built around that same knowledge base.

Creating an agent

From a file or folder's context menu, choose Create AI Agent and give it a name and optional description. This requires edit access to the target resource. A scope is fixed at creation time (one folder, recursively, or one file) and cannot be changed afterward — only the name, description, and active/inactive state can be edited later.

How the knowledge base works

There is deliberately no vector database, no embeddings, and no stored index. Every chat call walks the scoped folder or file live through the same storage-provider interface everything else in the app uses, extracts text from each file, and concatenates the largest/most-recent files first into the prompt — capped at 48,000 characters total, 40 files, and 12 folder levels deep. This means an edited or newly added file is reflected on the agent's very next answer with no re-indexing step, at the cost of silently truncating anything beyond those caps on a large document set. Extracted text is cached briefly in-process (keyed to each file's own version) to avoid redundant re-extraction within one conversation, but that cache doesn't survive a restart or scale across multiple server processes.

Chat: authenticated and public

  • Authenticated chat — any user with the agent's connection selected can chat while logged into C-ECM.
  • Public chat — every agent gets an unguessable public_token; anyone holding it can chat with no login at all, via a standalone page meant to be <iframe>-embedded on an external site. This is rate-limited (20 requests/60 seconds per token) because it triggers a real, potentially billed, LLM call with no authentication gate.

The auto-generated demo site

This is the closest thing in C-ECM to "generate a website with AI" — worth describing precisely, since it's easy to overstate. When an agent's owner first opens its test site link, C-ECM drafts a small marketing/support site (headline, About section, a handful of topic pages, a short blog, a contact page) automatically from the agent's own knowledge base.

What's actually generated

The page layout — header, hero, About card, page grid, blog, contact, chat widget — is a single fixed, hand-built template. The AI only ever generates the text content slotted into that template: a headline, subheadline, About copy, SEO description, footer tagline, and 2–6 pages plus 2–4 blog posts, each with a title and body. There is no path to prompt for a different layout, a different kind of application, or freeform HTML — every generation and edit action operates within this same fixed shape.

The generation prompts are explicitly instructed not to invent facts, third-party names, or claims not present in the source documents — a real, load-bearing instruction in the code, not just a description. Auto-generation is best-effort and fires only once per agent; on any failure (AI not configured, empty knowledge base) the site just shows generic fallback copy until someone clicks Regenerate with AI.

Beyond full regeneration, an owner can describe a targeted change in plain language (e.g. "change the accent color to green," "move Security first in the menu") — the model returns a minimal patch naming only what changes, never restructuring the page. A hand-editing path also exists: a WordPress-style admin bar with a Quill rich-text editor lets an owner write or fix content manually, upload real images (verified server-side as genuine image files, not trusted by filename), and manage pages/posts without AI involvement at all.

Who can edit the live site

Opening the authenticated Open test site action mints a short-lived (20-minute), single-agent-scoped edit token appended to the URL — this is what makes the admin bar appear, without ever putting a long-lived session token in a URL. Every write action against the live site (customize, page/post CRUD, AI generation, image upload) requires this token, except the static-site ZIP download, which only requires knowing the plain public token — the same trust level as viewing the site itself.

Static export

An owner can download the entire rendered site as a flat-file ZIP for hosting anywhere. The one thing that can't be exported is the chat widget itself, which unavoidably still calls back to this server for its actual AI logic.

Lead capture

The public chat widget has a scripted, fixed 3-question intake flow (email → phone → message) behind a "Contact us" quick reply — a simple client-side script, not an AI conversation. Submitted leads are visible to the agent's owner (or an admin) under the AI Agents report.

Management, stats, and admin reporting

An agent's owner sees chat count, total tokens used, last-used time, and lead count for their own agents. A separate manage_ai_agents_admin feature grants an org-wide view across every user's agents — useful for tracking overall LLM usage and adoption.

Known limitations

  • No cross-restart, cross-process caching of extracted knowledge-base text.
  • Rate limits are in-process and reset on server restart — not distributed across multiple server instances.
  • A single large document set can have content silently excluded once the 48,000-character/40-file/12-level caps are hit.
  • The full-site regeneration action (from the live admin bar) applies its whole draft immediately with no per-item review — unlike the same action called from inside the authenticated app, which hands back a draft for selective approval first.

AI Agent vs. workflow vs. traditional logic

Worth being precise about the distinction: a workflow (see Workflows & Approvals) is a deterministic, human-driven approval sequence with no AI involved at all. An AI Agent is a document-grounded conversational assistant — it answers questions and, for its demo site, drafts bounded template content; it does not take autonomous actions elsewhere in the app, call other tools, or make decisions on a user's behalf beyond what's described above.

Core Concepts / Content & Document Management

Content Management

Implemented

Content & Document Management

Folders and files behave the same way regardless of which storage backend a connection points at — every operation goes through one abstract provider interface, verified here in detail against the local-disk provider as the concrete reference implementation.

Verified baseline

The mechanics on this page are concretely verified against the local-disk provider's own SQLite schema and logic. Every other registered backend (FileNet, Google Drive, S3-compatible, and the rest — see Integrations & Connections) implements the same interface, but its exact fidelity to trash emulation, versioning, and locking should be treated as provider-specific rather than assumed identical.

Folders

Create, browse (with a breadcrumb trail), rename, and move folders. Moving a folder into itself or one of its own descendants is explicitly blocked (HTTP 400). There is no folder-level batch API — selecting several items and moving them in the UI simply loops the single-item endpoint once per item, reporting each failure individually.

Files

Upload (multipart, up to FD_MAX_UPLOAD_BYTES, 500 MiB by default), download/preview, rename, and move. Note the upload size limit is enforced after the file is fully read into memory — it rejects an oversized file rather than streaming a hard cap. Download and in-app preview are literally the same endpoint; the audit log can't distinguish "the user opened this to look at it" from "the user downloaded it" and deliberately records both as the same "viewed" event.

Versioning

Every upload to an existing file creates a new version rather than overwriting; nothing is ever deleted from version history via the API. Restoring an earlier version doesn't roll back in place — it appends a brand-new version whose content matches the one you restored, so version history only ever grows, and the "restored" version is itself just one more entry you could later restore away from.

Check-out / check-in

A file can be checked out (locked) to prevent conflicting concurrent edits. This is a C-ECM-side bookkeeping lock, not a native lock on every backend — for providers with no locking of their own (S3, Azure Blob, local disk, Google Drive), this registry is the only enforcement; providers with real native locking (FileNet's CE-API checkout/checkin) are expected to enforce it themselves as well. Uploading a new version while a file is checked out to someone else returns HTTP 423 Locked, naming the current holder. Checking back in is allowed for the lock holder or a superadmin — deliberately, so a checkout from someone no longer available can still be released.

Trash, restore, and permanent delete

Deleting a folder or file moves it to Trash (soft delete) rather than destroying it immediately; it can be restored from there, or permanently deleted later. Permanently deleting a folder also purges every one of C-ECM's own local records tied to it and its entire subtree — tags, comments, share links, custom metadata, e-signature records, workflow references, AI agent references, and access grants — not just the content itself. Trash fidelity is explicitly acknowledged in the code as varying by backend (some providers emulate it with a hidden folder rather than a true soft-delete flag).

Trash listing is unfiltered

Unlike every other folder/file view, the Trash listing is not filtered by per-resource access grants — a trashed item's ancestor chain usually can't be walked to check it. Restoring an item out of Trash is still access-checked normally.

Share links

Generate a tokenized public URL for a specific file, optionally with an expiry (1–365 days) and a password. A share link's role (view/comment/edit) is stored and returned by the API, but today the public link-opening endpoint doesn't differentiate by role at all — every role currently just returns the file's raw bytes; there's no public comment-submission or public-edit path yet. Password verification uses a salted SHA-256 hash described in the code's own comment as "a lightweight deterrent, not an auth-grade KDF" — not bcrypt/argon2/PBKDF2. Failed password attempts are rate-limited in-memory (5 per 5 minutes per link) but that limiter resets on a server restart. Share links only ever work for files, never folders.

Tags

Implemented

A single, deployment-wide set of color-coded labels any user can create and attach to or detach from a file or folder. Tags are entirely C-ECM's own overlay — they never sync to or read from a backend's native tagging (Google Drive Labels, Box metadata, etc.). Any authenticated user can create a tag and attach/detach it on anything they can view — tagging something you can see doesn't require edit rights. Permanently deleting a tag definition is a separate, more sensitive action (it cascades off every resource on every connection at once) and requires the dedicated manage_tags feature.

Comments

Partial

Freeform comments on a file or folder, with resolve/reopen state. The data model genuinely supports one level of reply-threading and @mentions, but the shipped UI never uses either — every comment renders as a flat, unthreaded list with no reply or mention picker; threading and mentions are reachable only by calling the API directly. Editing or deleting a comment's text is restricted to its author (or a superadmin); resolving/reopening stays a collaborative, view-level action, since a reviewer other than the original author legitimately needs to be able to close out a discussion.

Document classes (content modeling)

Implemented

An administrator defines reusable metadata schemas — a name plus an ordered list of typed fields (text, number, date, boolean, or select) — analogous in spirit to a FileNet document class or an Alfresco content model, but implemented as C-ECM's own uniform layer rather than mapped onto any backend's native classification system. No classes are seeded by default — a fresh install starts with zero classes; every example below is something an admin would create, not a shipped default.

Example class configurations (illustrative)

Invoice — fields: vendor (text, required), amount (number). Contract — fields: party (text), status (select: Draft / Final / Archived).

Managing class definitions requires the manage_document_classes feature. Field types, required-ness, and per-class key uniqueness are UI conventions enforced by the settings form — the API itself does not reject an invalid type string or a duplicate field key.

Assigning metadata to a resource

Implemented

Assign a class to a file or folder and fill in its field values (edit-level access required); optionally cascade the same class and values onto an entire folder's subtree in one action. Every change is recorded to a per-resource history you can review as a field-by-field before/after diff. Submitted values are validated against the assigned class's field definitions before they're stored — a missing required field, a non-numeric value for a number field, or a value outside a select field's declared options is rejected (422) rather than silently accepted.

Cascade is a one-time stamp

Cascading to a subfolder copies the class and values onto every descendant once, at that moment — it's not a live link. A file added to the folder afterward, or a change made later, doesn't propagate automatically.

Retention & legal hold

Implemented

An administrator defines named retention policies — a retention period in days and an action to take once a record is overdue: review (flag for a human), archive, or auto_delete. Any user can then enroll a specific file or folder under an existing policy, which computes a due date from that moment.

A background scheduler sweeps for overdue records every hour (and can be triggered on demand by an administrator) and genuinely carries out the configured action:

  • auto_delete — really trashes the resource (soft delete, recoverable like any other trash item, not a permanent delete).
  • review — marks the record "under review" for a human to act on; nothing is touched automatically.
  • archive — Status-only marks the record "archived" but moves no data anywhere — there is no cold-storage/tiering destination in this application. Documentation and expectations should treat this as a status marker, not a storage action.

Legal hold exempts a specific enrolled record from the scheduler entirely, regardless of how overdue it is — enforced directly in the scheduler's own query, and deliberately gated behind the manage_retention feature (an ordinary viewer being able to clear a hold would defeat its purpose).

Re-enrollment resets state

Enrolling the same resource under the same policy a second time resets its status back to active and clears any legal hold that record had — a direct consequence of how enrollment is implemented, not a documented feature.

Core Concepts / Search

Search

Implemented

Search

Search one connection at a time, or fan out across every connection at once — described in the codebase's own comments as the feature no other lightweight ECM client offers: searching every connected backend simultaneously.

Single-connection search

GET /search?q=... delegates entirely to the active connection's own provider implementation — what actually gets matched (a filename substring, a metadata field, real full-text content) genuinely varies by backend. As one concrete example, the CMIS provider issues a cmis:name LIKE '%query%' query — a filename match, not full-text search. Results are filtered by the caller's per-resource access level after the provider returns them, so a restricted hit is silently omitted rather than causing the whole search to fail; there is no pagination.

Global (cross-connection) search

GET /search/global queries every configured connection in parallel via a real thread pool, not sequentially. The whole fan-out is capped at 15 seconds total (not per connection) — any connection still running when that shared deadline hits is reported as timed out in a per-connection error map alongside the results, rather than blocking everything else. A failing or slow connection never hides results from the others. OAuth credentials that need refreshing mid-search (Microsoft Graph and Box both rotate their refresh token on every use) are refreshed and persisted immediately, specifically so a search doesn't quietly break that connection's next refresh anywhere else in the app.

Saved searches

Partial

Save a named query (free text + an optional file-type filter + an optional tag filter) and re-run it later — only its owner (or a superadmin) can delete it. Two real gaps worth knowing: the tag-id filter is accepted and stored but never actually applied when a saved search runs — it's currently a no-op. And a saved search always re-runs against whichever connection your session currently has active, not necessarily the connection it was originally saved against.

Search & permissions

Both single-connection and global search filter out any hit the caller doesn't have at least view-level access to (see Security) — but only after the provider has already returned its full result set; the filtering isn't a query-level constraint.

Reporting, Audit & Notifications

Every recorded action flows through one place — the activity log — which then fans out to two independent channels: an in-app notification inbox, and outbound webhooks. A subscriber failure never breaks the action that triggered it.

Activity / audit log

A single, cross-connection record of every action C-ECM takes — content changes, logins, admin changes, workflow transitions, e-signature and retention events, AI agent chats — filterable by connection, resource, event type, actor, and date range, with CSV export. Gated behind the view_activity_log feature (the router's own comments note this used to have no access check at all, a real gap since fixed).

Summary analytics

GET /activity/summary returns totals, unique-actor counts, and breakdowns by event type, by actor (top 20), and by calendar day — the closest thing this application has to a reporting dashboard. There is no general-purpose report builder, scheduled report delivery, or custom-query report designer.

Burst-detection alerts

Exactly two hardcoded, narrowly-scoped alert rules run over the log — not a general anomaly-detection system:

  • Danger: 3 or more failed logins by the same actor within any 15-minute window (possible credential stuffing).
  • Warning: 5 or more deletes by the same actor within any 10-minute window (possible accidental or malicious bulk deletion).

There is no IP or geolocation data captured anywhere in the log, so location- or device-based anomaly detection ("new device," "unusual location") isn't possible with what's recorded today.

In-app notifications

A personal, per-user inbox with unread tracking. Notifications fire only for a fixed set of 20 event types (content changes, workflow transitions, tagging, sharing, check-out/in, legal hold) — everything else recorded to the activity log (logins, e-signature events, AI agent chats, file views, partial workflow votes) never produces a notification. Fan-out today is broadcast to every active user, not just people with access to the affected resource — there's no per-user relevance targeting or mute/preference mechanism yet.

Webhooks

Register an external destination — a custom URL, a Slack incoming webhook, or a Discord webhook — to receive a real-time HTTP POST when matching events occur. Unlike in-app notifications, webhooks have no fixed event-type whitelist: any event the app ever records can be subscribed to, filtered only by each webhook's own configured list (empty = everything).

  • Payloads. Custom destinations get the raw event JSON, HMAC-SHA256 signed with that webhook's own secret (encrypted at rest, and never echoed back once set — only reported as "configured"); Slack/Discord get a short one-line human-readable summary, unsigned (the destination URL itself is the secret).
  • Security. Outbound URLs are validated against SSRF — private, loopback, and link-local addresses are rejected, re-checked again at delivery time to defend against DNS rebinding, with redirects disabled.
  • Delivery. Up to 3 attempts with a short exponential backoff, dispatched from a background thread — a deliberately simple mechanism, not a durable queue; a failed delivery is recorded but not automatically retried later.
  • Scoping. A webhook is always scoped to a connection and a specific resource at creation time; an "unscoped, fires on everything" webhook can only be reached afterward, via an update, not created directly.
Scope depth is shallow

A webhook scoped to a folder matches events on that folder and on items whose immediate parent is that folder — not anything nested two or more levels deeper. There's no ancestor-chain walk for webhook scoping the way there is for access grants.

Email

Not implemented There is no email-sending capability anywhere in this application — no SMTP client, no outbound mail queue, no email templating. If you need an email alert for something, route it through a custom webhook to a service that sends the email on your behalf.

Administration

Administration

Almost the entire administration surface — every integration's credentials, AI backend selection, and SSO configuration — funnels through two endpoints: GET /admin/settings and PUT /admin/settings, both gated by the manage_admin_settings feature. User, group, workflow, retention, and webhook management each have their own dedicated screens, covered on their own pages.

Users & groups

See Security for the full authorization model. In short: create users under Settings → Users, create groups and grant them features under Settings → Groups, and assign users to groups from the same screen. There are no fixed roles to choose from — only the features you've explicitly granted a group.

Storage-provider connections

Two different things live under Settings → Connections, easy to conflate but administratively distinct:

  • Per-user connections — any user can connect their own account to a backend (credentials or OAuth consent), reachable without any admin feature.
  • App-level OAuth registration — before anyone can connect via OAuth to Google Drive, Microsoft 365, Box, Dropbox, and 13 other OAuth providers, an administrator must register one shared OAuth app's client id/secret for that provider (in the provider's own developer console first, then entered here). This is what manage_admin_settings actually gates.

Of 17 OAuth-based providers, 6 (Google, Microsoft, Box, Dropbox, Laserfiche, ShareFile) can also be pre-seeded via environment variables before first login; the other 11 must be entered through this settings screen or the API at least once. One provider, Evernote Teams, is explicitly labeled in its own settings form as non-functional even once configured — its API doesn't fit this app's connection model.

SAML SSO

Partial Configured under Settings → SSO: your Identity Provider's entity id, SSO URL, and signing certificate, plus which group new SSO-created users default into. C-ECM's own SP signing keypair is generated automatically on first use — nothing to configure for that half. As with DocuSign below, this integration is real, working code that has not been exercised end-to-end against a live Identity Provider in this environment.

DocuSign e-signature

API-only, no admin UI Fully implemented and persisted the same way as everything else in this section, but there is currently no settings screen for it — an administrator configures DocuSign's integration key, user id, account id, private key, environment, and webhook HMAC key either as environment variables or by calling PUT /admin/settings directly (the live Swagger UI at /docs is the easiest way to do this without writing a script). See Configuration Reference for exact field names.

AI backend selection

API-only, no admin UI Same situation as DocuSign: switching the active AI backend and supplying IBM Watson-family credentials is fully wired (and takes effect immediately, no restart needed) but has no dedicated settings screen yet — set it via environment variables or PUT /admin/settings. One asymmetry worth knowing: if you choose openai or ollama as the backend, those two backends' own connection details are environment-variable-only and do need a restart to change — only the three IBM Watson-family backends (watsonx, watson_nlu, watson_disco) are live-configurable through this settings surface.

Webhooks, workflow definitions, retention policies

Each has its own dedicated management screen under Settings, gated by its own feature (manage_webhooks, manage_workflow_definitions, manage_retention respectively) rather than manage_admin_settings — see Reporting, Audit & Notifications, Workflows & Approvals, and this page's retention section.

How settings are stored

Every one of the roughly 61 admin-configurable values described above lives in one flat SQLite key-value table (settings.db). Every secret-shaped one among them (OAuth client secrets, the auto-generated SAML SP private key, the DocuSign private key and its incoming-webhook HMAC key, IBM Watson/watsonx API keys) is encrypted at rest — see Security. The SAML IdP's own certificate is public by nature and stays plain text, same as every other non-secret setting. GET /admin/settings additionally never echoes a secret's actual value back, only a boolean "is this set" flag, so a client-side leak can't expose it either.

Because secrets are never echoed back, saving settings treats a blank/omitted field as "leave unchanged" — the one deliberate exception is the SAML on/off switch, handled as a real boolean specifically so that turning SSO off can't be silently ignored as a falsy empty value.

Architecture

System Architecture

A FastAPI backend and a React single-page frontend, talking over a plain JSON REST API — no message queue, no separate database server, no microservices. Everything the backend needs to run is either an in-process Python module or a local SQLite file.

Backend architecture

Each concern owns its own module pair — a *_store.py (pure SQLite access: connection, schema, CRUD, additive-only migrations) and a thin routers/*.py (HTTP boundary: request validation, auth dependency, calls the store). A handful of concerns that need business logic beyond plain storage add a third *_service.py layer in between (e.g. retention_service.py wraps retention_store.py with the actual due-action logic; ai_agents_service.py wraps ai_agents_store.py with knowledge-base gathering). This pattern repeats consistently across every subsystem in the app rather than varying module to module.

There is no ORM — every store module hand-writes SQL via Python's built-in sqlite3, using WAL journal mode and a busy-timeout on every connection. Every database is its own file under one data directory (see Configuration Reference's FD_DATA_DIR), so there is no single monolithic schema and no cross-concern SQL joins — a router that needs data from two concerns (e.g. deleting a connection and purging its tags, comments, and workflow references) makes explicit calls into each store in turn.

The storage-provider abstraction

Every backend integration (see Integrations & Connections) implements one abstract StorageProvider interface (folders, files, versions, search, sharing, and more) in storage_providers/base.py. Routers never talk to a specific backend directly — they resolve session.provider from whichever connection is active and call the same methods regardless of what's on the other end. Every id (a folder id, a file id, a version id) is treated as an opaque string whose real shape is entirely up to that provider — a local SQLite integer, a FileNet GUID, a Google Drive file id — which is why routers that need to walk an ancestor chain (for trash cleanup, or for resource-level access checks) do so by repeatedly calling get_children/get_file live, rather than joining against a locally mirrored folder tree. C-ECM does not mirror any connected backend's folder structure in its own database, except incidentally for the one connection that happens to be the local-disk provider.

Authentication & authorization architecture

See Security for the full model. Structurally: a shared auth.require_feature("...") dependency gates every protected route by group-granted feature, with superadmin bypassing all of them; a separate access_control.require_resource_level(...) call, made explicitly near the top of folder/file/comment/tag/lock/share/workflow handlers, gates per-resource view/edit access on top of that.

Frontend architecture

A React 19 single-page app built with Vite and TypeScript, with no router library (confirmed directly from package.json — the only runtime dependencies are react, react-dom, mammoth for DOCX preview, and xlsx for spreadsheet preview). Every "page transition" is a nested useState conditional render, not a URL change:

  1. App shell (App.tsx) picks Landing, Login, or the main Drive app purely from auth state.
  2. Drive-level view ("mine" | "trash" | "workflows" | "global-search") switches between the folder grid, the Approvals hub, and Global Search.
  3. Document viewer is a nullable overlay state, with its own tab sections as plain toggled <details> elements.
  4. Settings is a fourth independent overlay with its own nested tab state, each tab client-side gated by the same feature check used for the real server-side gate.
No deep-linking

Because nothing here touches the URL or browser history, refreshing the page always returns to the app's root view, there's no shareable link to a specific folder or settings tab, and the browser's back/forward buttons do nothing inside the app.

Two module-level singletons (not React state) carry the current bearer token and active connection id, read by a single shared API client (api/client.ts) so every fetch call — from any component, not just ones with access to context — automatically attaches Authorization and X-Connection-Id. A registered global 401 handler forces a full logout from anywhere in the app the moment any request comes back unauthorized.

Other extension points

Add it to notification_service._NOTIFIABLE_EVENT_TYPES only if it should also produce an in-app notification.
  • New workflow-adjacent features — the workflow engine (Workflows & Approvals) is a good structural reference for a multi-step, permission-gated process: a store, a router, and a small set of well-named exceptions the router maps to specific HTTP status codes.

Business Use Cases

Business Use Cases

C-ECM has no industry-specific modules — no "Healthcare edition," no built-in HR content types. Every scenario below is the same generic toolkit (connections, folders, tags/metadata, workflows, access grants, retention) applied to a different domain's documents and process. Read these as illustrative configurations you'd build, not features you'd switch on.

Human Resources

Problem: employee records scattered across shared drives with inconsistent access control. Approach: connect the HR document repository as its own connection; create a "Personnel File" document class with fields like employee ID, department, and document type; restrict the whole HR root folder with an access grant to an "HR" group; route new-hire paperwork through an "Employee Onboarding" workflow (manager review → HR sign-off).

Legal

Problem: contract review happens over email with no version control or audit trail. Approach: a "Contract Review" workflow (legal review → counterparty negotiation notes → final sign-off), each revision tracked automatically as a new file version; on execution, send the final document for signature via e-signature; enroll executed contracts under a "Contracts: 10-year retention, then review" retention policy.

Finance

Problem: invoice approval requires manual routing and has no spend visibility. Approach: a multi-step "Invoice Approval" workflow with quorum (two of three finance approvers); use AI's workflow-suggestion feature to auto-route newly scanned invoices toward the right workflow; the activity log gives a full audit trail of who approved what and when for a compliance review.

Healthcare

Problem: patient documents need strict, narrow access control with a defensible audit trail. Approach: per-patient or per-department folders locked down via access grants to specific care-team groups; every view, download, and edit lands in the activity log; a "Records: retain, then review" retention policy with legal hold available the moment litigation or an audit is anticipated.

Not a compliance certification

C-ECM provides the access-control, audit, and retention mechanisms a regulated environment needs — it is not independently certified against HIPAA or any other regulatory framework. Compliance is the deploying organization's responsibility to establish and document.

Banking

Problem: customer documentation compliance requires proof of who accessed what, when. Approach: the cross-connection activity log and its CSV export are the audit surface; group-scoped access grants restrict customer files to the account team; a "Compliance Review" workflow gates any exception approval.

Insurance

Problem: claims documents need classification and key-field extraction before routing. Approach: a "Claim" document class with structured fields; AI classification suggests the right class and drafts field values from the uploaded document (available via the API today; see its documentation for the current UI gap); a claims-review workflow routes it to an adjuster.

Government

Problem: records-management rules require defensible, scheduled disposition. Approach: a per-record-series retention policy (e.g. "auto_delete after 7 years"), enforced automatically by the hourly retention scheduler, with legal hold available the moment a records request or FOIA matter arises.

Manufacturing

Problem: engineering and quality documents need version-controlled review before release. Approach: an "Engineering Change Review" workflow (design review → quality sign-off → release), with every revision preserved in version history so a prior approved revision is never actually lost, only superseded.

Operate / Operations & Troubleshooting

Operations

Operations & Troubleshooting

C-ECM runs as a single backend process against local SQLite files — straightforward to operate, with real, honestly-stated limits on concurrency and scale that are worth knowing before you hit them.

Performance & scalability

  • Single-process by design. There's no built-in horizontal scaling, load balancing, or shared-state layer across multiple backend instances — every SQLite file, every in-memory session table, and every in-process rate limiter (webhook delivery, public AI Agent chat/lead/image endpoints, share-link password attempts) lives in that one process's memory and resets on restart. Running two instances behind a load balancer would each maintain their own independent copy of all of this.
  • SQLite, not a database server. Every store uses WAL journal mode with a busy-timeout, which handles moderate concurrent access well, but there is no connection pooling or read-replica story — this is appropriate for a single-team or single-department deployment, not a high-concurrency multi-tenant service.
  • Global search is genuinely parallel (a real thread pool, one worker per connection, capped at 15 seconds total), so search performance scales with the slowest connection, not the sum of all of them.
  • Large uploads are buffered in memory before the size limit is checked — a very large permitted upload (close to the 500 MiB default) means that much memory used transiently per concurrent upload.

Backup & restore

Covered in Installation & Deployment — in short, there's no built-in scheduler; back up by copying the data directory's SQLite files while the server is stopped.

Activity Log

Document Class
An admin-defined schema of metadata fields that can be assigned to a resource, C-ECM's equivalent of a content type.

Legal Hold
A flag on a retention record that exempts it from any automatic due-date action, regardless of how overdue it is.

Resource
A file or folder within a connection, identified by an opaque, provider-defined id.

A named rule: keep enrolled records for N days, then review/archive/auto_delete. See Content & Document Management.

A user flag that bypasses every Feature and Access Grant check outright.

Release Notes

Release Notes

There is no formal semantic-versioning scheme yet — this page traces the project's real development history from its commit log rather than inventing version numbers that don't exist.

Origin

C-ECM began as a hackathon build (originally named "FileDrive") developed for an IBM watsonx/TechXchange hackathon submission, which is why the AI subsystem is built specifically around IBM watsonx and Watson NLU/Discovery rather than a generic multi-vendor AI abstraction. It has since grown well past that original scope.

Current baseline — documented as "Release 1.0"

What this documentation describes, in the order it was substantially built out:

  • Core content management: folders, files, versioning, check-out/check-in, trash/restore, tags, comments, document classes.
  • Search: single-connection and parallel cross-connection global search, saved searches.
  • Sharing: tokenized, optionally password-protected and time-limited share links.
  • 54 storage-backend connectors behind one common interface — 2 verified live, 52 unverified/config-required/stub (see Integrations & Connections).
  • Approval workflows: multi-step, quorum-based, with e-signature and retention/legal-hold.
  • AI document intelligence (summarize/ask/classify/suggest-workflow) and AI Agents (scoped chat assistants with an auto-generated demo site).
  • Webhooks, in-app notifications, and a cross-connection activity/audit log with burst-detection alerting.
  • Full group/feature-based access control, replacing an earlier fixed admin/editor/viewer role model, plus SAML SSO login.
  • Per-resource (file/folder) view/edit access grants, opt-in and layered on top of group features.
  • Multi-document workflow requests, group-based step assignment, and mid-flight reassignment — the most recent workflow enhancement, replacing an earlier one-document-per-request, users-only-assignee model.
  • A documented, discoverable public REST API (this documentation, plus the live /docs Swagger UI).
  • Encryption at rest for connection credentials and every secret-shaped admin setting, plus authorization fixes closing four gaps a full codebase audit surfaced: comment edit/delete restricted to the author, tag-definition deletion restricted to a dedicated feature, saved-search deletion restricted to its owner, and document-class metadata values validated against their schema — the most recent security/data-integrity pass.

Notable internal migrations

Three schema/model changes worth knowing if you're working against data from an earlier point in the project's history — all apply automatically, additively, on startup, with no manual migration step required:

  • The old fixed admin/editor/viewer role list was replaced by the Group/Feature model described in Security; existing accounts were carried forward automatically (old admin → superadmin, old editor-only accounts → a seeded "Legacy Editors" group).
  • Workflow steps' reviewers (a plain username list) were replaced by assignees (user-or-group references); any existing workflow definition is upgraded automatically the first time the server starts against it.
  • Every existing connection's stored credentials, and every existing secret-shaped admin setting, are transparently re-encrypted in place the first time the server starts against them — no plaintext row is ever left behind after the first startup post-upgrade.

Upgrade considerations

Every store module's migrations are additive-only — new columns and tables are added, nothing is ever dropped — so upgrading is simply deploying newer code and restarting (see Installation & Deployment). There are no breaking database changes to plan around today.

Connect & Extend / Integrations & Connections

Integrations

Integrations & Connections

54 storage backends are registered behind one common interface. Read this page before choosing one for production use — the honest, code-disclosed confidence level varies enormously across the list, and that distinction matters more than the raw count.

The single most important fact on this page

Of the 54 registered connectors, only 2 — Local Disk and IBM FileNet — are presented in the codebase's own comments as verified, trustworthy integrations. Every one of the other 52 carries an explicit, honest disclosure in its own source file that it was written against a vendor's published API documentation but has never been exercised against a real, live account of that service. A long provider list should not be read as 54 field-tested integrations — it's 2 verified ones plus 52 structurally-complete, untested implementations at varying levels of documentation confidence (detailed below).

What a connection is

A connection is one stored, authenticated link between C-ECM and a specific account/instance of a backend. Any authenticated C-ECM user can create a credentials-based connection or start an OAuth consent flow (no admin feature required) — only deleting a connection, and registering the shared OAuth app credentials some providers need before anyone can connect to them at all, are admin-gated. Every connection's credentials are encrypted at rest — see Security.

What every provider gets for free

Two capabilities are defined once and apply identically to all 54 providers, since they're C-ECM's own layer rather than anything backend-specific:

  • Share links (see Content & Document Management) — always a C-ECM-hosted broker link, never a backend's own native share URL, even for providers (Google Drive, Box, SharePoint) that have real native sharing of their own.
  • Native permissions listing — Not implemented a defined extension point (a provider can opt in and expose its backend's real ACLs) that zero of the 54 registered providers currently implement; calling it always returns a 501.
